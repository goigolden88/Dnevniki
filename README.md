# Дневники

Персональное PWA вместо набора дневников в Obsidian: циклическое обслуживание, здоровье, потребление контента.

**https://goigolden88.github.io/Dnevniki/**

Открывается в браузере, ставится иконкой на телефон, работает без сети. Данные лежат в браузере и без настройки никуда не уходят.

**Как поставить и настроить** — [docs/07-Установка](docs/07-Установка.md): iPhone, Android, компьютер, синхронизация. Всё ниже — для того, кто хочет свою копию приложения и дорабатывать её (Р-77).

## Своя копия

Приложение — статический сайт на GitHub Pages. Бэкенда нет, данные у каждого свои. Своя копия — это форк, который GitHub собирает и публикует сам.

1. **Fork** на странице репозитория. Имя оставь `Dnevniki` — сайт встанет на `https://<логин>.github.io/Dnevniki/` без единой правки. Другое имя — поправь `BASE` в `vite.config.ts` на `/<имя>/`: при неверном `base` сборка проходит зелёной, а страница открывается белой (Р-17).
2. **Actions.** На форке GitHub выключает workflow, пришедшие вместе с оригиналом. Вкладка Actions форка — кнопка, которая их включает.
3. **Pages.** Settings → Pages → Build and deployment → Source → **GitHub Actions**. Без этого деплой упадёт на последнем шаге с «Not Found».
4. **Первый деплой.** Actions → «Деплой на GitHub Pages» → Run workflow — или любой пуш в `main`. Workflow гоняет тесты, собирает и публикует.

Что стоит знать:

- **Записи не переезжают сами.** Копия на другом адресе — для браузера другой сайт, и база у неё своя. Переносятся синхронизацией с тем же репозиторием данных или файл-копией ([07-Установка](docs/07-Установка.md))
- **Отчёты об ошибках** — «Сообщить об ошибке» в приложении открывает issue в репозитории, с адреса которого открыт сайт, то есть в твоём форке. Включи там Issues: Settings → General → Features (Р-78)
- **Название и иконка** — `manifest` в `vite.config.ts`. Иконки рисует `npm run icons` из `public/favicon.svg` (Р-20)
- **Обновления автора** — «Sync fork» на странице форка. Где правились одни и те же файлы, будет конфликт; разбирается руками или агентом
- **Документы после форка — твои.** Журнал и Решения автора — история того, почему код такой. Свои записи их продолжают: Журнал — сверху, Решения — ниже. Если собираешься подтягивать обновления автора, номера решений и `id` в `src/changes.ts` у вас столкнутся; свои решения удобно нумеровать со своей буквой

## Доработка с агентом

Проект ведётся с Claude Code с первого дня и устроен так, чтобы агент подхватывал его без пересказа.

- **`docs/` — источник истины.** Имена полей и типы — из `02-Архитектура`, а не придумываются заново. Отступление от неё называется до кода
- **`CLAUDE.md` — правила кода и работы.** Claude Code читает его сам. Codex читает `AGENTS.md`, README не читает никто, — поэтому стартовый промпт ниже велит прочитать `CLAUDE.md` явно (Р-77)
- **Порядок работы** — `docs/06-Процесс.md`: план → подтверждение → код; решение пишется в `05-Решения` в момент выбора; видимое изменение — строка в `src/changes.ts` в том же коммите; в конце сессии — запись в Журнал
- **Новый модуль** — по чеклисту «Как добавить модуль» в `02-Архитектура`
- **Отзывы — issues.** Агенту достаточно ссылки на issue; коммит со словами «Fixes #N» закрывает его сам

Первая сессия в своей копии:

```
Это моя копия проекта «Дневники» — форк. Прочитай README.md, CLAUDE.md
и все файлы docs/ перед началом: документы — источник истины, код им
подчиняется. Правила из CLAUDE.md обязательны, в какой бы программе ты
ни работал.

Журнал и Решения до этой сессии — история автора оригинала. Мои решения
пишутся ниже, Журнал продолжается сверху.

Что я хочу сделать: <задача>.
Сначала план работ, код — после подтверждения. Отступления от
02-Архитектура.md и от прежних решений называй до кода.
```

Следующие сессии — заготовки в `docs/06-Процесс.md`, «Шаблоны».

Проверки перед пушем — те же, что у автора:

- `npm run test` — расчёт. Итог — по коду выхода, а не по выводу
- `npm run smoke` — собирает приложение и проходит его в headless-браузере (Р-41). Нужен Chromium на машине, свой путь — переменная `CHROME_PATH`. В облачной среде агента браузера может не оказаться — тогда прогон гоняется у себя перед пушем
- Миграция схемы — ещё `npm run check:data -- <копия>` и `npm run smoke -- --data <копия>` на свежей копии своих данных (Р-72)

Деплой гоняет только тесты и сборку. Прогон он не заменяет.

## На вырост

Ничего из этого не построено. Описано, чтобы тот, кто дорабатывает, выбрал сам: что даёт, как устроить, что тронуть и чего стоит.

### Напоминание в точное время и на iPhone — пуш через GitHub Actions

Сейчас напоминания будит браузер: только Chrome на Android у установленного приложения, и время выбирает он (Р-50, Р-57). Точное время и iPhone даёт только пуш с сервера. Сервером может стать GitHub Actions в репозитории данных (Р-66):

1. Пара ключей VAPID. Публичный — в приложение, настройкой, а не константой (Р-15). Приватный — в секреты репозитория данных
2. Приложение подписывается через `pushManager.subscribe` и показывает подписку текстом. Её кладут в секреты репозитория данных — по одной на устройство
3. Workflow по расписанию (`schedule`) в репозитории данных берёт данные и код приложения — он публичный — и считает просроченное той же `cycleStates` из `modules/cycles/cycles.ts`: расчёт без React и без базы, в node он работает как есть. Потом отправляет пуш, например пакетом `web-push`
4. В `src/sw.ts` — обработчик `push`, который показывает уведомление. Тап уже обработан: `notificationclick` ведёт по адресу из уведомления

Оговорки. Расписание Actions идёт по UTC и под нагрузкой может опаздывать — это «около девяти утра», а не будильник. На iPhone пуш приходит только установленному приложению, iOS 16.4 и новее, и разрешение спрашивается по нажатию. Раннер GitHub читает данные — то же доверие, что к самому репозиторию данных. Бесплатных минут Actions на ежедневный запуск хватает с запасом.

### Календарь

Самое простое — без ключей и без сервера: кнопка «В календарь» на экране позиции (`modules/cycles/`). Дата — поле `next` у `cycleState`, «когда ожидается следующий раз». Два пути:

- ссылка на создание события Google Календаря (`calendar.google.com/calendar/render?action=TEMPLATE&text=…&dates=…`) — открывает готовое событие
- файл `.ics` с событием и напоминанием — его открывает календарь и на iPhone, и на Android

Календарь напомнит в точное время на любом телефоне. Цена: событие — снимок. Отметил раньше или позже — дата в календаре устарела, добавлять заново. Держать календарь в курсе само умеет только Google Calendar API со входом, а доступ из браузера без сервера живёт час: обновлять можно по кнопке, не фоном.

### Свой сервер

Снимает сразу три ограничения: пуш в точное время и на iPhone без Actions, хранилище без GitHub, вход без токена. Цена — всё, от чего проект отказался в `01-Проект`, «Границы»: бэкенд, его хостинг, вход, CORS и резервные копии уже на нём. Local-first при этом остаётся: сервер — ещё одно место для копии, а не путь записи (Р-05).

### Другое хранилище вместо GitHub

Разобрано в Р-75:

| Вариант | Телефон | Компьютер | Цена |
|---|---|---|---|
| Другой git-хостинг (GitLab, Codeberg) | да | да | пустит ли запросы из браузера (CORS) — выяснять |
| Папка на компьютере (File System Access) | нет: на Android и iPhone выбора папки нет | Chrome, Edge | разрешение на папку браузер может спрашивать заново |
| Dropbox | да | да | регистрация приложения под адрес своей копии; вход переадресацией, на iPhone может вернуться в Safari, а не в приложение |
| Google Drive | доступ живёт час, продление — по тапу | | фоновая синхронизация не выживает |
| Свой сервер (WebDAV и т. п.) | да | да | сервер, CORS, вход |

Папка, выбранная внутри Dropbox или Яндекс.Диска на компьютере, заодно становится копией в облаке и связывает компьютеры между собой; телефон при этом не участвует.

Как подключать:

- **Другой git-хостинг** — правка `core/github.ts`: тот же набор операций — голова ветки, дерево, файл, коммит, сдвиг ветки без `force`. Отпечаток файла у любого git один и тот же
- **Хранилище без git** — ещё и прохода в `core/sync.ts`. Он думает деревом, отпечатками git и коммитами, а `planUpload` сравнивает отпечаток, посчитанный у себя, с деревом на сервере (Р-33). Путь, который предлагался и не выбран (Р-75): вынести общий интерфейс хранилища. Снимок «версия и отпечатки файлов»; чтение файла; запись со ссылкой на версию, от которой читали, — ушла, значит конфликт, и проход перечитает и сольёт заново; свой способ считать отпечаток; проверка доступа. GitHub становится одной реализацией, новое хранилище — второй. Модули, экраны, база и правило слияния от этого не меняются
- В обоих случаях — поля в `ui/SyncSettings.tsx`, текст о синхронизации в справке `screens/Help.tsx`, ключи в `settings`. `settings` не синхронизируется никогда: там токен
- **Проверять на живом сервисе.** Первая синхронизация с GitHub упала на пустом репозитории, хотя тест на этот случай был зелёным: он проверял догадку о поведении GitHub, а не сам GitHub (Р-32)

## Команды

```
npm install
npm run dev       # разработка, service worker включён
npm run build     # проверка типов и сборка в dist/
npm run preview   # посмотреть собранное
npm run test      # тесты расчёта
npm run smoke     # прогон собранного приложения в браузере
npm run icons     # перерисовать иконки PWA из public/favicon.svg

npm run check:data -- <копия>   # миграции и расчёт на копии настоящих данных
npm run smoke -- --data <копия> # все экраны на копии настоящих данных
```

`npm run smoke` собирает приложение, открывает его в headless-браузере и проходит обычный путь человека через все три модуля, ленту и настройки. Отвечает на один вопрос — открывается ли приложение и не падает ли на обычном пути. Тестов экранов в проекте нет и не будет, это замена им (Р-41). Нужен любой браузер на Chromium; свой путь задаётся переменной `CHROME_PATH`.

`npm run icons` запускается руками и только при смене иконки. В сборку не входит.

## Деплой

Пуш в `main` → GitHub Actions собирает и публикует на Pages. Ручных шагов нет.

Однократная настройка, если репозиторий разворачивается заново: **Settings → Pages → Source → GitHub Actions**. Без неё workflow отработает и упадёт на последнем шаге с «Not Found».

## Подводные камни

**`base` в `vite.config.ts` равен имени репозитория** — `/Dnevniki/`. Pages отдаёт сайт проекта не с корня домена. При неверном `base` сборка проходит зелёной, а страница открывается белой, и все скрипты уходят в 404. Переименуете репозиторий — правьте эту строку.

**Service worker обновляется сам.** Свой, `src/sw.ts`: новая сборка забирает управление немедленно и перезагружает страницу. Имя на выходе — `sw.js`, менять нельзя: установленные копии остались бы со старым работником навсегда. Проверить, что обновление доехало до телефона, можно по дате сборки в «Настройки» → «О приложении».

**Секретов в этом репозитории нет и не будет** — он публичный. Токен доступа к репозиторию данных — поле в настройках приложения, хранится только в браузере.
