# Архитектура

Обновлён: 10.09.2026
Версия схемы данных: 1

## Стек

- **Vite + React + TypeScript**
- Роутинг через хеш (`#/today`) — на GitHub Pages обычные пути дают 404 при обновлении страницы. Библиотека `react-router-dom`, `HashRouter`
- Сайт живёт по `/Dnevniki/`, а не в корне домена: `base` в `vite.config.ts` равен имени репозитория. См. Р-17
- Стили обычным CSS, без Tailwind
- Хранилище на устройстве — IndexedDB
- Service worker для офлайна, установки иконкой и напоминаний о просроченном. Свой файл `src/sw.ts`, собирается `injectManifest` (Р-50)
- Бэкенда нет

## Два репозитория

| Репозиторий | Что внутри | Видимость |
|---|---|---|
| Код приложения | исходники, сборка, GitHub Pages | публичный |
| Данные | JSON-файлы с записями | приватный |

Pages для приватного репозитория требуют платного тарифа, поэтому код публичный. Секретов в нём нет по определению. Токен доступа вводится руками в настройках приложения и хранится только в браузере — в код он не попадает никогда.

## Модель данных

Две категории сущностей: **справочники** (что отслеживаем) и **события** (что произошло).

### Общая часть

```ts
type Base = {
  id: string          // ULID, генерируется локально, сортируется по времени
  updatedAt: string   // ISO 8601, время последнего изменения записи
  deleted?: boolean   // метка удаления, не вычищается никогда
}
```

### Справочники

```ts
type CycleItem = Base & {
  name: string
  cat: string                  // Гигиена | Дом | Техника | Авто | Дача
  group?: string               // куст внутри категории, свободная строка (Р-30)
  intervalDays: number | null  // null → считаем медиану по истории
  archived?: boolean
  note?: string
}

type Tag = Base & {
  name: string
  scope: 'symptom' | 'activity'
}

type Template = Base & {
  label: string                // пусто → подпись из названий позиций
  kind: EventKind
  preset: Record<string, unknown>
  order: number
}

// Заготовка по виду. Сейчас шаблоны заводятся только для циклов (Р-49):
//   kind 'cycle' → { marks: { itemId: string; price?: number }[] }
// Заготовка приезжает из синхронизации и разбирается модулем с проверкой
// формы: кривая заготовка даёт пустую кнопку, а не падение экрана.

// Какого типа событие создаёт шаблон быстрого ввода.
// Ровно пять событийных сущностей, описанных ниже. См. Р-19.
type EventKind = 'cycle' | 'episode' | 'measure' | 'session' | 'content'
```

### События

```ts
type CycleEvent = Base & {
  itemId: string
  date: string        // YYYY-MM-DD, дата события, не дата ввода
  price?: number
  note?: string
  refs?: string[]
}

type Episode = Base & {
  title: string
  source: 'self' | 'doctor'
  start: string
  end: string | null  // null → эпизод продолжается
  symptoms: string[]  // id тегов
  note?: string
  refs?: string[]
}

type Measure = Base & {
  metric: string      // weight | height | bp | произвольная
  date: string
  value: number
  value2?: number     // второе значение, например диастолическое давление
  note?: string
}

type Session = Base & {
  activity: string    // id тега
  date: string
  durationMin?: number
  distanceKm?: number
  note?: string
  refs?: string[]
}

type ContentEntry = Base & {
  type: 'anime' | 'series' | 'film' | 'game' | 'book' | 'course'
  title: string
  titleOrig?: string
  start: string | null    // YYYY-MM-DD или YYYY-MM (Р-25), null → "к просмотру"
  end: string | null      // тот же формат, что start
  status: 'planned' | 'active' | 'done' | 'dropped'
  score: number | null    // 1..10, шаг 0.1 (Р-26)
  comment?: string
  ext?: { source: string; id: string; cover?: string }
  refs?: string[]
}
```

### Заметки по модели

- **Замена вещи и процедура — одна структура.** Событие обнуляет счётчик, промежуток между событиями и есть срок службы. Флешка и стрижка описываются одинаково, разница только в словах на экране.
- **`refs` зарезервировано под связи между модулями.** Сейчас не используется. Понадобится, когда обострение поясницы нужно будет связать с пропущенными тренировками.
- **`date` и `updatedAt` — разные вещи.** Первое — когда произошло, второе — когда запись правили. Ввод задним числом обязателен.

## Раскладка данных в репозитории

```
meta.json                 { schemaVersion }
items.json                позиции циклов
tags.json                 теги
templates.json            шаблоны ввода
cycles/2026.json          отметки циклов за год
health/episodes.json
health/measures.json
health/sessions.json
content/2026.json
content/undated.json      записи без разбираемого года (Р-34)
```

Нарезка по годам: прошлые годы после закрытия не переписываются вообще. Без нарезки каждая отметка щётки переписывала бы всю базу и раздувала историю коммитов.

Запись, у которой года нет — список «к просмотру» с пустым `start`, — уезжает в `undated.json` того же модуля. Туда же попадает запись с испорченной датой: потерять её из-за одной кривой строки нельзя (Р-34).

Файлы, положенные в репозиторий руками (README и прочее), приложение не трогает и не читает.

Раскладка описана таблицей в `core/layout.ts` — это единственное место, где она известна.

## Синхронизация

**Принцип: local-first.** Запись сохраняется на устройстве и отражается на экране до всякой сети. Синхронизация — фоновый процесс, который может отставать или падать, не ломая работу.

Порядок:

1. Запись падает в IndexedDB, экран обновляется мгновенно
2. Изменённые записи помечаются грязными — это признак «есть что отправлять», а не список файлов (Р-18, Р-33)
3. Через пять секунд после последнего действия запускается проход. Также при открытии приложения, при возврате вкладки из фона и при возврате сети
4. Читаем голову ветки и дерево файлов — два запроса. Скачиваем только те свои файлы, чей отпечаток разошёлся с запомненным на прошлом проходе
5. Сливаем их в базу, затем пересобираем дерево из базы целиком и отправляем одним коммитом только разошедшиеся файлы (Р-32, Р-33)
6. Ветка ушла вперёд → перечитываем и сливаем заново. Максимум две попытки, потом откладываем
7. Одна синхронизация — один коммит. Нет сети — очередь ждёт

Тихий проход, когда ничего не менялось, — два запроса и ни одного коммита.

Репозиторий без единого коммита — особый случай: Git Data API его не обслуживает. Первый файл кладётся через Contents API, и только это заведение даёт второй коммит; дальше правило «одна синхронизация — один коммит» выполняется всегда (Р-32).

Порядок «сначала влить чужое, потом отправить своё» обязателен: дерево собирается из базы целиком, и отправка до слияния затёрла бы на сервере всё, чего у нас ещё нет. Поэтому любая ошибка чтения обрывает проход до записи.

### Правило слияния

**Для каждой записи по `id` побеждает версия с более поздним `updatedAt`.**

Добавление, правка и удаление обрабатываются одинаково. Побеждает последняя правка *отдельной записи*, а не последняя версия файла целиком — иначе запись с телефона затирала бы запись с компа.

Удалённые записи остаются как метки `deleted: true` навсегда. Если их вычищать, второе устройство при следующей синхронизации их воскресит.

### Ручная синхронизация

Кнопкой в «Настройках» скачивается и загружается **один файл-слепок**, а не раскладка выше (Р-23):

```
{ schemaVersion, exportedAt, data: { <хранилище>: [записи] } }
```

Включает все синхронизируемые хранилища вместе с надгробиями. `settings` не входит — там токен. Загрузка сливается по общему правилу: по записи, побеждает поздний `updatedAt`. Форма файла проверяется до записи; файл чужой схемы отвергается целиком.

Раскладка по файлам остаётся форматом репозитория данных — она нужна git, а не человеку.

## Локальное хранилище

IndexedDB, не localStorage: у второго лимит около 5 МБ и синхронный API, который подвесит интерфейс на импорте.

Настройки хранятся отдельно и **не синхронизируются**: в них токен доступа, а «когда я в последний раз синхронизировался» у каждого устройства своё.

| Ключ | Что лежит |
|---|---|
| `syncEnabled` | включена ли синхронизация. По умолчанию нет |
| `syncRepo` | `владелец/репозиторий` данных |
| `syncToken` | fine-grained токен. В выгрузку не попадает никогда |
| `syncBranch` | ветка, по умолчанию `main` |
| `syncTokenExpires` | когда истекает токен: из заголовка ответа GitHub либо вписано руками |
| `syncLastAt` | время последнего успешного прохода |
| `syncLastCommit` | коммит, на котором сошлись в последний раз |
| `syncTree` | отпечатки файлов на тот же момент: путь → sha |
| `lastExportAt` | когда в последний раз забирали копию файлом |
| `reminderLastDay` | в какой день уже приходило напоминание — не чаще раза в день (Р-50, Р-54) |
| `folds` | какие блоки экрана свёрнуты: id блока → да/нет (Р-55) |

**У каждого устройства свой токен.** Настройки не синхронизируются, поэтому телефон настраивается отдельно от компьютера: репозиторий вписывается заново, токен вставляется заново. Это не недоделка — иначе токен пришлось бы класть в общий репозиторий.

Выпускать лучше отдельный токен на устройство, а не переносить один и тот же. Потерянный телефон тогда отзывается одной кнопкой в GitHub, не ломая компьютер. И сам секрет никуда не едет: токен выпускается прямо на том устройстве, где будет жить, — GitHub показывает его ровно один раз.

## Структура кода

```
src/
  core/
    model.ts     типы, версия схемы, миграции
    db.ts        обёртка над IndexedDB
    sync.ts      проход, слияние, состояние, запуск по событиям
    layout.ts    раскладка записей по файлам репозитория
    github.ts    тонкий клиент API
    dates.ts     разбор, формат, дельты, склонения
    id.ts        генерация ULID
    feed.ts      строка ленты и общие операции над ней (Р-48)
  modules/
    cycles/      экраны и логика интервалов
    health/
    content/
    <имя>/       внутри каждого модуля одно и то же:
      <имя>.ts     расчёт — без React и без db, покрыт тестами
      labels.ts    тексты
      feed.ts      строки ленты и раздел markdown (Р-48)
      use<Имя>.ts  работа с db
  ui/            общие компоненты
  screens/
    Today.tsx
    Feed.tsx
    Settings.tsx
  registry.ts    таблица видов событий (Р-48)
  notify.ts      напоминание о просроченном (Р-50)
  sw.ts          service worker
  app.tsx
```

**Правила, которые соблюдаются жёстко:**

- `core` не знает про модули
- Модули не знают друг про друга — только через `refs` и общую ленту
- `ui` не знает про модули; модули пользуются `ui` (Р-51)
- Все модули разом знают только `app.tsx`, `registry.ts`, `notify.ts` и `screens/`
- К хранилищу обращаются только через `db`, напрямую в IndexedDB не ходит никто
- Работа с GitHub спрятана за `sync` — замена на нормальный бэкенд должна быть правкой одного файла

## Как добавить модуль

Модули устроены одинаково, и появление четвёртого — правка по списку, а не переделка. Порядок:

1. **`core/model.ts`** — типы записей модуля, имена хранилищ в `SYNCED_STORES`, строки в `StoreRecord`, новые виды событий в `EventKind`
2. **`core/db.ts`** — индексы нового хранилища в `INDEXES`
3. **`core/model.ts`** — миграция: поднять `SCHEMA_VERSION` и добавить шаг в `migrations`. Шаг обязан **сам создать хранилище и его индексы**: `createStores` выполняется только для свежей базы, на существующих устройствах он не сработает. Поставить `additive: true`, если форма прежних записей не меняется
4. **`modules/<имя>/`** — расчёт, экраны, работа с `db`. Логика модуля живёт здесь, а не в `core` (Р-24)
5. **`core/layout.ts`** — строка в `PLACES`: одним файлом или нарезкой по годам, и по какой дате берётся год
6. **`app.tsx`** — маршрут, при необходимости вкладка в `ui/Layout.tsx`
7. **`src/registry.ts`** — строка на каждый вид события модуля: подпись, строки ленты и раздел markdown из `modules/<имя>/feed.ts`. Компилятор не соберёт приложение, пока строки нет

Чего делать **не** нужно: править `db`, сам проход синхронизации или соседние модули. Если понадобилось — граница нарушена, и это повод остановиться.

Пятый пункт — сознательное исключение: раскладка обязана быть где-то одна, и из двух зол (`sync` знает про модули или модуль знает про раскладку) выбрано меньшее. Дописывается строка, а не правится механика.

## Реестр видов событий

Общая лента — единственное место, где модули встречаются по данным. Реестр — таблица `{ [K in EventKind]: … }` в `src/registry.ts` (Р-48):

```ts
KINDS = {
  cycle: { label: 'Циклы', feed: …, markdown: … },
  …
}
```

- Ключ — вид события, а не модуль: лента и markdown работают с событиями, у здоровья их три вида
- Модуль отдаёт чистые функции из `modules/<имя>/feed.ts`, реестр только сводит их в таблицу
- `core/feed.ts` знает строку ленты, но не модули: вид записи — `EventKind` из модели
- Маршруты, вкладки и блоки «Сейчас» через реестр не идут — это продуктовые решения, из списка они не выводятся

Лента читает все хранилища сама, вместе с надгробиями справочников: у отметки удалённой позиции название должно остаться.

## Версионирование схемы

`meta.json` содержит `schemaVersion`. При загрузке данных версия сверяется, при отставании применяются миграции по порядку. Заводится с первого дня: модель будет меняться, и без версии старые данные однажды перестанут читаться.

## Известные слабые места

| Риск | Смягчение |
|---|---|
| Токен лежит в браузере | fine-grained токен на один репозиторий, только содержимое. Лежит открытым текстом: спрятать его на устройстве негде, доступ к разблокированному устройству — это доступ к данным |
| Токен на каждом устройстве отдельно | свой токен на устройство, потерянное отзывается по одному |
| Токен протухает раз в год | срок виден в «Настройках», предупреждение за 30 дней, отдельный текст ошибки на отказ по токену |
| Задержка сети при записи | local-first, сеть никогда не в критическом пути |
| Конфликт версий файла | перечитать и слить заново, слияние по записям |
| Раздувание истории коммитов | пачками, нарезка по годам |
| Лимит 5000 запросов в час | не грозит при отправке пачками |
| GitHub недоступен | приложение работает локально, синхронизация отстаёт |
