# Архитектура

Обновлён: 07.09.2026
Версия схемы данных: 1

## Стек

- **Vite + React + TypeScript**
- Роутинг через хеш (`#/today`) — на GitHub Pages обычные пути дают 404 при обновлении страницы. Библиотека `react-router-dom`, `HashRouter`
- Сайт живёт по `/Dnevniki/`, а не в корне домена: `base` в `vite.config.ts` равен имени репозитория. См. Р-17
- Стили обычным CSS, без Tailwind
- Хранилище на устройстве — IndexedDB
- Service worker для офлайна и установки иконкой
- Бэкенда нет

## Два репозитория

| Репозиторий | Что внутри | Видимость |
|---|---|---|
| Код приложения | исходники, сборка, GitHub Pages | публичный |
| Данные | JSON-файлы с записями | приватный |

Pages для приватного репозитория требуют платного тарифа, поэтому код публичный. Секретов в нём нет по определению. Токен доступа вводится руками в настройках приложения и хранится только в браузере — в код он не попадает никогда.

## Модель данных

Две категории сущностей: **справочники** (что отслеживаем) и **события** (что произошло).

### Общая часть

```ts
type Base = {
  id: string          // ULID, генерируется локально, сортируется по времени
  updatedAt: string   // ISO 8601, время последнего изменения записи
  deleted?: boolean   // метка удаления, не вычищается никогда
}
```

### Справочники

```ts
type CycleItem = Base & {
  name: string
  cat: string                  // Гигиена | Дом | Техника | Авто | Дача
  group?: string               // куст внутри категории, свободная строка (Р-30)
  intervalDays: number | null  // null → считаем медиану по истории
  archived?: boolean
  note?: string
}

type Tag = Base & {
  name: string
  scope: 'symptom' | 'activity'
}

type Template = Base & {
  label: string
  kind: EventKind
  preset: Record<string, unknown>
  order: number
}

// Какого типа событие создаёт шаблон быстрого ввода.
// Ровно пять событийных сущностей, описанных ниже. См. Р-19.
type EventKind = 'cycle' | 'episode' | 'measure' | 'session' | 'content'
```

### События

```ts
type CycleEvent = Base & {
  itemId: string
  date: string        // YYYY-MM-DD, дата события, не дата ввода
  price?: number
  note?: string
  refs?: string[]
}

type Episode = Base & {
  title: string
  source: 'self' | 'doctor'
  start: string
  end: string | null  // null → эпизод продолжается
  symptoms: string[]  // id тегов
  note?: string
  refs?: string[]
}

type Measure = Base & {
  metric: string      // weight | height | bp | произвольная
  date: string
  value: number
  value2?: number     // второе значение, например диастолическое давление
  note?: string
}

type Session = Base & {
  activity: string    // id тега
  date: string
  durationMin?: number
  distanceKm?: number
  note?: string
  refs?: string[]
}

type ContentEntry = Base & {
  type: 'anime' | 'series' | 'film' | 'game' | 'book' | 'course'
  title: string
  titleOrig?: string
  start: string | null    // YYYY-MM-DD или YYYY-MM (Р-25), null → "к просмотру"
  end: string | null      // тот же формат, что start
  status: 'planned' | 'active' | 'done' | 'dropped'
  score: number | null    // 1..10, шаг 0.1 (Р-26)
  comment?: string
  ext?: { source: string; id: string; cover?: string }
  refs?: string[]
}
```

### Заметки по модели

- **Замена вещи и процедура — одна структура.** Событие обнуляет счётчик, промежуток между событиями и есть срок службы. Флешка и стрижка описываются одинаково, разница только в словах на экране.
- **`refs` зарезервировано под связи между модулями.** Сейчас не используется. Понадобится, когда обострение поясницы нужно будет связать с пропущенными тренировками.
- **`date` и `updatedAt` — разные вещи.** Первое — когда произошло, второе — когда запись правили. Ввод задним числом обязателен.

## Раскладка данных в репозитории

```
meta.json                 { schemaVersion }
items.json                позиции циклов
tags.json                 теги
templates.json            шаблоны ввода
cycles/2026.json          отметки циклов за год
health/episodes.json
health/measures.json
health/sessions.json
content/2026.json
```

Нарезка по годам: прошлые годы после закрытия не переписываются вообще. Без нарезки каждая отметка щётки переписывала бы всю базу и раздувала историю коммитов.

## Синхронизация

**Принцип: local-first.** Запись сохраняется на устройстве и отражается на экране до всякой сети. Синхронизация — фоновый процесс, который может отставать или падать, не ломая работу.

Порядок:

1. Запись падает в IndexedDB, экран обновляется мгновенно
2. Изменённые записи помечаются грязными. Сворачивает их в список файлов `sync`, не `db` — см. Р-18
3. Через несколько секунд после последнего действия запускается отправка. Также при открытии приложения и при возврате сети
4. Читаем удалённые файлы с их версиями → сливаем → пишем обратно с указанием версии
5. Версия устарела → перечитываем и сливаем заново. Максимум две попытки, потом откладываем
6. Одна синхронизация — один коммит. Нет сети — очередь ждёт

### Правило слияния

**Для каждой записи по `id` побеждает версия с более поздним `updatedAt`.**

Добавление, правка и удаление обрабатываются одинаково. Побеждает последняя правка *отдельной записи*, а не последняя версия файла целиком — иначе запись с телефона затирала бы запись с компа.

Удалённые записи остаются как метки `deleted: true` навсегда. Если их вычищать, второе устройство при следующей синхронизации их воскресит.

### Ручная синхронизация

Кнопкой в «Настройках» скачивается и загружается **один файл-слепок**, а не раскладка выше (Р-23):

```
{ schemaVersion, exportedAt, data: { <хранилище>: [записи] } }
```

Включает все синхронизируемые хранилища вместе с надгробиями. `settings` не входит — там токен. Загрузка сливается по общему правилу: по записи, побеждает поздний `updatedAt`. Форма файла проверяется до записи; файл чужой схемы отвергается целиком.

Раскладка по файлам остаётся форматом репозитория данных — она нужна git, а не человеку.

## Локальное хранилище

IndexedDB, не localStorage: у второго лимит около 5 МБ и синхронный API, который подвесит интерфейс на импорте.

Настройки (репозиторий, токен, предпочтения) хранятся отдельно и **не синхронизируются**.

## Структура кода

```
src/
  core/
    model.ts     типы, версия схемы, миграции
    db.ts        обёртка над IndexedDB
    sync.ts      очередь, слияние, состояние
    github.ts    тонкий клиент API
    dates.ts     разбор, формат, дельты, склонения
    id.ts        генерация ULID
  modules/
    cycles/      экраны и логика интервалов
    health/
    content/
  ui/            общие компоненты
  screens/
    Today.tsx
    Feed.tsx
    Settings.tsx
  app.tsx
```

**Правила, которые соблюдаются жёстко:**

- `core` не знает про модули
- Модули не знают друг про друга — только через `refs` и общую ленту
- К хранилищу обращаются только через `db`, напрямую в IndexedDB не ходит никто
- Работа с GitHub спрятана за `sync` — замена на нормальный бэкенд должна быть правкой одного файла

## Как добавить модуль

Модули устроены одинаково, и появление четвёртого — правка по списку, а не переделка. Порядок:

1. **`core/model.ts`** — типы записей модуля, имена хранилищ в `SYNCED_STORES`, строки в `StoreRecord`
2. **`core/db.ts`** — индексы нового хранилища в `INDEXES`
3. **`core/model.ts`** — миграция: поднять `SCHEMA_VERSION` и добавить шаг в `migrations`. Шаг обязан **сам создать хранилище и его индексы**: `createStores` выполняется только для свежей базы, на существующих устройствах он не сработает. Поставить `additive: true`, если форма прежних записей не меняется
4. **`modules/<имя>/`** — расчёт, экраны, работа с `db`. Логика модуля живёт здесь, а не в `core` (Р-24)
5. **`app.tsx`** — маршрут, при необходимости вкладка в `ui/Layout.tsx`

Чего делать **не** нужно: править `db`, `sync` или соседние модули. Если понадобилось — граница нарушена, и это повод остановиться.

Общая лента — единственное место, где модули встретятся. Реестра модулей нет намеренно: пока лента не написана, проектировать его не из чего.

## Версионирование схемы

`meta.json` содержит `schemaVersion`. При загрузке данных версия сверяется, при отставании применяются миграции по порядку. Заводится с первого дня: модель будет меняться, и без версии старые данные однажды перестанут читаться.

## Известные слабые места

| Риск | Смягчение |
|---|---|
| Токен лежит в браузере | fine-grained токен на один репозиторий, только содержимое |
| Токен протухает раз в год | перевыпуск вручную на обоих устройствах |
| Задержка сети при записи | local-first, сеть никогда не в критическом пути |
| Конфликт версий файла | перечитать и слить заново, слияние по записям |
| Раздувание истории коммитов | пачками, нарезка по годам |
| Лимит 5000 запросов в час | не грозит при отправке пачками |
| GitHub недоступен | приложение работает локально, синхронизация отстаёт |
