# Решения

Какие были развилки, что выбрали и почему. Отвечает на вопрос «почему так, а не иначе».
Записывается в момент выбора, чтобы через месяц не переобсуждать заново.

---

### Р-01 · Своё приложение, а не плагины Obsidian
05.09.2026

Dataview и Templater закрыли бы около 70% задачи за дни вместо месяцев. Выбрано своё приложение: цель не только решить задачу, но и построить вещь, плюс Obsidian на телефоне неудобен для быстрого ввода, а быстрый ввод — корень проблемы.

### Р-02 · PWA, не нативная разработка
05.09.2026

Даёт установку иконкой, офлайн и уведомления без сторов и без второй кодовой базы. Ограничение принято: на `file://` service worker не работает, нужен http — локальный сервер или Pages.

### Р-03 · Три модуля, а не один универсальный дневник
05.09.2026

Циклы, эпизоды и потребление требуют разной механики ввода и разной аналитики. Попытка свести их к одному экрану и была причиной, по которой прежняя система казалась бессмысленной.

### Р-04 · Политический дайджест и кешбеки остаются в Obsidian
05.09.2026

Не имеют структуры «событие с датой». Это текст и правила, в событийной модели им плохо.

### Р-05 · Local-first, IndexedDB
05.09.2026

Сеть не должна быть в критическом пути записи, иначе мгновенный отклик — главная фича — умирает. localStorage отвергнут: лимит ~5 МБ и синхронный API, подвешивающий интерфейс на импорте.

### Р-06 · Хранилище данных — GitHub, два репозитория
05.09.2026

Бесплатно, без своего сервера, с историей изменений и откатом, данные в читаемом виде. Публичный репозиторий для кода (Pages для приватного платные, секретов в коде нет), приватный — для данных.

Отвергнуто: свой бэкенд (избыточен для одного пользователя), облачные диски (нет нормального API из браузера).

### Р-07 · Слияние: последняя правка побеждает, по записи
05.09.2026

Изначально рассматривался чистый журнал добавлений, но он не позволяет править и удалять. Выбрано: каждая запись хранит `updatedAt`, при слиянии по `id` берётся более поздняя версия.

Ключевое: сравнение по *записи*, а не по файлу целиком. Иначе запись с телефона затирает запись с компа. Переделывать это потом дорого, поэтому зафиксировано до начала кода.

Удалённые записи остаются метками навсегда — иначе второе устройство их воскресит.

### Р-08 · Нарезка данных по годам
05.09.2026

Иначе каждая отметка переписывает всю базу и раздувает историю коммитов. Прошлые годы после закрытия не трогаются.

### Р-09 · TypeScript
05.09.2026

Проект идёт через много бесед, и без типов модель данных расползётся между сессиями — в новой беседе неизвестно, как назывались поля. Сборка через Vite нужна в любом случае, лишнего шага не появляется.

### Р-10 · Хеш-роутинг
05.09.2026

На GitHub Pages обычные пути дают 404 при обновлении страницы.

### Р-11 · Импорт из Obsidian вручную, парсер не пишем
05.09.2026

Файлов немного, а форматов дат три вперемешку. Содержимое приводится к JSON в отдельной беседе и загружается файлом. Писать парсер под разовую задачу невыгодно.

### Р-12 · Внешние базы контента — необязательная кнопка
05.09.2026

Shikimori, TMDB, RAWG подтягивают обложки и метаданные. Но ручной ввод остаётся основным путём: нет сети или не нашлось — записал руками, ничего не блокируется.

### Р-13 · Физическая активность — в модуль здоровья
05.09.2026

Связь травм и нагрузки — то, что дневник должен показывать. Тип данных третий (сессия с метриками), но модуль тот же. Граница с будущим тайм-менеджером: здесь фиксируется факт, там планируется намерение.

### Р-14 · Замена вещи и процедура — одна структура
05.09.2026

Событие обнуляет счётчик, промежуток между событиями и есть срок службы. Разделять флешку и стрижку незачем, разница только в словах на экране.

### Р-15 · Репозиторий и токен — настройки, а не константы
05.09.2026

Иначе приложением невозможно поделиться. Посторонний получает режим по умолчанию: данные в браузере, синхронизации нет, перенос экспортом. Своя синхронизация — опция для тех, кто заведёт репозиторий и токен.

### Р-16 · Пуши откладываются на поздний этап
05.09.2026

На Android веб-пуши работают нормально и добавляются потом без переделок архитектуры.

### Р-17 · `base` сборки — `/Dnevniki/`
07.09.2026

GitHub Pages отдаёт сайт проекта не с корня домена, а по `/<имя репозитория>/`. Репозиторий называется `Dnevniki`, значит адрес — `https://goigolden88.github.io/Dnevniki/`, и `base` в `vite.config.ts` обязан быть `'/Dnevniki/'`.

Записано отдельным решением потому, что ошибка здесь диагностируется плохо: при неверном `base` сборка проходит зелёной, а страница открывается белой, и все скрипты отдают 404. Выглядит как сломанная сборка, лечится одной строкой конфига.

Следствие: переименование репозитория ломает адрес. `base`, `start_url`, `scope` и `navigateFallback` правятся вместе с ним.

Отвергнуто: вычислять `base` в CI из `GITHUB_REPOSITORY`. Переживает переименование, но прячет от читателя конфига единственное число, которое здесь важно.

### Р-18 · Грязными помечаются записи, а не файлы
07.09.2026

Уточняет шаг 2 порядка синхронизации в `02-Архитектура.md` («затронутые файлы помечаются грязными»). `core/db.ts` копит ссылки вида `{store, id}`, а раскладку этих записей по файлам (`cycles/2026.json` и прочая нарезка по годам) делает `core/sync.ts` на Этапе 2.

Причина: если `db` знает про имена файлов и нарезку по годам, он знает про способ хранения на сервере. Тогда замена GitHub на бэкенд перестаёт быть правкой одного файла — а это требование того же самого документа. Результат для синхронизации идентичен, граница между слоями цела.

### Р-19 · `EventKind` — пять значений
07.09.2026

В `02-Архитектура.md` поле `Template.kind` объявлено как `EventKind`, но сам тип нигде не описан — пропуск при проектировании. Заполняется перечнем событийных сущностей, которые в модели уже есть: `'cycle' | 'episode' | 'measure' | 'session' | 'content'`.

Ничего не выдумано и модель не изменена: это ровно список того, что в ней описано. Шаблон быстрого ввода — кнопка, создающая событие, и `kind` отвечает на вопрос, событие какого типа она создаёт.

Все пять заводятся сразу, хотя экраны под здоровье и контент появятся только на Этапах 3–4: добавление значения в перечень позже потребовало бы правки модели и повышения версии схемы ради одной строки.

### Р-20 · Иконки PWA генерируются своим скриптом
07.09.2026

`scripts/icons.mjs` рисует четыре PNG из той же геометрии, что лежит в `public/favicon.svg`. Запускается руками (`npm run icons`), результат коммитится, в сборку не входит.

Причина: штатный `@vite-pwa/assets-generator` тянет `sharp`, `sharp` тянет `libvips`, у которого на сегодня четыре CVE (GHSA-f88m-g3jw-g9cj). Обходного пути нет — версия прибита в зависимостях генератора. Ради четырёх картинок из скруглённых прямоугольников это несоразмерная цена, тем более что растеризатор нужен раз в год.

В скрипте только `zlib` из стандартной библиотеки: свой кодировщик PNG и сглаживание перебором 4×4. `npm audit` чистый.

Цена решения: рисовать в этой иконке что-то сложнее прямоугольников нельзя. Понадобится — ставим настоящий растеризатор тогда, а не заранее.

### Р-21 · Список «к просмотру» — статус в ContentEntry, не отдельная сущность
07.09.2026

Формально задевает границу «здесь факт, там намерение» из 01-Проект (тайм-менеджер, ещё не начат): пункт «хочу посмотреть» — это намерение, не событие. Но граница проводилась для распределения времени, а не для конкретных тайтлов контента — по существу не нарушение.

Отдельная сущность-справочник (по аналогии с CycleItem/CycleEvent, с «превращением» в ContentEntry при начале просмотра) отвергнута: лишняя механика ради, по сути, одного поля разницы — тот же принцип, что в Р-14 (не плодить сущности там, где хватает статуса).

Расширен ContentEntry: `status` получает значение `'planned'`, `start` становится nullable. Модуль 3 не реализован (Этап 4), существующих записей нет — миграция не нужна, правится только тип в `model.ts`.

### Р-22 · Порог статуса — 80% медианы, медиана — по последним пяти интервалам
07.09.2026

В 01-Проект перечислены пять статусов позиции, но «подходит к сроку» нигде не определено. Определяется так: позиция желтеет, когда с последней отметки прошло 80% медианного интервала, и краснеет после 100%.

Порог долевой, а не в днях. Фиксированные «N дней до срока» на коротких циклах держат позицию в предупреждении почти всегда, а на длинных предупреждают слишком поздно. Доля даёт запас, пропорциональный самому циклу: у позиции с медианой 45 дней предупреждение приходит за 9, у трёхдневной — за полдня. Порог общий на всё приложение, отдельного поля в позиции нет — по тому же принципу, что в Р-14 и Р-21.

Медиана считается по последним пяти интервалам, а при меньшем числе — по всем имеющимся. Причина в данных: в гигиене отметки обрываются в мае, и медиана по всей истории тянула бы расчёт к привычке полугодовой давности. Скользящее окно отражает то, как позиция ведётся сейчас. Пять — компромисс: меньше даёт дёрганый интервал, больше возвращает ту же инерцию.

Отбрасывание выбросов не делается: медиана к ним устойчива по построению. Разрыв в данных при этом остаётся видимым — пропуск в мае даёт один длинный интервал, который в разбросе на экране истории заметен, а на медиану почти не влияет.

### Р-23 · Ручной перенос — один файл-слепок, а не раскладка репозитория
07.09.2026

Уточняет и отменяет абзац «Ручная синхронизация» в 02-Архитектура, где было сказано, что кнопкой скачиваются «те же JSON-файлы», что лежат в репозитории данных. Код с Этапа 0 делает другое, и правым признан код.

Формат: `{ schemaVersion, exportedAt, data: { <хранилище>: [записи] } }`. Один файл на всё.

Причина: раскладка по файлам и нарезка по годам существуют ради git — чтобы отметка щётки не переписывала базу целиком и не раздувала историю коммитов. У файла, который человек руками пересылает себе в мессенджер, истории нет, и делить его на девять частей не для чего. На телефоне девять файлов ещё и не собрать обратно без ошибок.

Что входит: все синхронизируемые хранилища целиком, вместе с надгробиями `deleted: true` — иначе второе устройство воскресит удалённое. Что не входит: `settings`, там токен доступа.

Файл со схемой ниже текущей отвергается с явной ошибкой, пока не написана миграция содержимого. Файл со схемой выше — тоже, с предложением обновить приложение. Форма файла проверяется до записи (`db.parseSnapshot`), при несходстве отвергается целиком: половина импортированных данных хуже внятного отказа.

### Р-24 · Логика модуля живёт в модуле, аддитивная миграция не ломает файлы
07.09.2026

Два решения об одном: что должно быть правдой, когда появится четвёртый модуль.

**Расчётная логика модуля лежит в `modules/<имя>/`, а не в `core`.** Исправляет отступление, допущенное на Этапе 1: `cycles.ts` был написан в `core`, хотя структура кода в этом документе отводит модулю «экраны и логику интервалов». Формально правило «core не знает про модули» не нарушалось — `core` этот файл не импортировал. По сути нарушалось: в ядре лежало знание про конкретный модуль, и здоровье с контентом повторили бы приём. Файл перенесён в `modules/cycles/cycles.ts`.

**Отставание схемы само по себе не отвергает файл-слепок.** Раньше `importAll` отвергал любой файл с версией ниже текущей. Добавление модуля поднимает `SCHEMA_VERSION`, не трогая записи прежних модулей, — и по старому правилу появление здоровья сделало бы нечитаемыми все выгрузки, сделанные до него. При том что по Р-23 файл-слепок и есть способ увезти данные, это потеря единственной копии на ровном месте.

Теперь шаг миграции несёт флаг `additive`: изменение только добавляет хранилище, индекс или необязательное поле. Файл отвергается, только если между его версией и текущей есть хотя бы один шаг с `additive: false` — то есть форма записей действительно менялась. Ошибка называет причину словами из `note` этого шага.

Цена: флаг ставится руками, и неверный `true` тихо пропустит в базу записи старой формы. Проверка формы на входе (`db.parseSnapshot`) от этого не спасёт — она сверяет только `id` и `updatedAt`.

### Р-25 · Даты контента допускают месячную точность
08.09.2026

`ContentEntry.start` и `end` хранят либо `YYYY-MM-DD`, либо `YYYY-MM`. Остальные модули по-прежнему только полный день.

Причина в данных: в дневнике просмотренного заголовок раздела — месяц, дня нет нигде. Из 72 записей ни у одной нет числа. Ставить день `01` значило бы записать выдумку фактом: через год никто не вспомнит, что «начал 1 января» — не то, что было в дневнике.

Отдельное поле точности рядом с полной датой отвергнуто: это лишнее поле в модели, бамп схемы и обязанность помнить о нём в каждом месте, где дата показывается. Забыть его один раз — и выдумка снова становится фактом. Строка `2026-01` несёт свою точность в себе, забыть невозможно.

Тип в модели не меняется — `start` и так `string | null`. Меняется договорённость и разбор. Лексикографическая сортировка продолжает работать: `2026-01` < `2026-01-05` < `2026-02`.

Цена: к таким датам нельзя применять `daysBetween` и прочую арифметику по дням. Для контента она не нужна ни в одной запланированной фиче — итоги года считаются по году, «начато против закончено» по факту наличия даты. Функции `dates.ts` кидают на месячной дате, а не молча врут, — проверка `isMonthStr` заведена рядом.

### Р-26 · Оценка контента — шаг 0.1
08.09.2026

`score` остаётся `number | null` в диапазоне 1..10, но допускает один знак после запятой. Фактически это стобалльная шкала, делённая на десять.

В переносимых данных встречаются только половинки (5.5, 6.5, 7.5, 8.5), но ограничивать шагом 0.5 незачем: тип уже `number`, а разница между 6.4 и 6.6 автору осмысленна. Округление при импорте отвергнуто — оно теряет информацию безвозвратно, а вернуть её потом неоткуда.

Цена: распределение оценок в итогах года нельзя строить по сырым значениям — 91 возможное значение вместо 10. На графике оценки группируются по целым, дробная часть остаётся в карточке записи. Решается на Этапе 4.

### Р-27 · Срок по истории считается с трёх интервалов
08.09.2026

Дополняет Р-22, который задал правило медианы, но забыл нижнюю границу. Без границы расчёт молча считал сроком одно наблюдение: у зубной щётки две отметки, один промежуток в 137 дней — и на экране появлялось «раз в 137 дней по истории». У таймера полива один промежуток в 28 дней давал красную полосу и «перебор 24 дня».

Теперь интервал по истории выводится, только если промежутков не меньше трёх, то есть отметок не меньше четырёх. Ниже порога позиция получает статус «срок не задан» с пояснением «отметок N из 4».

Три, а не два: медиана из двух — это их среднее, и разброс между ними ничем не ограничен (85 и 67 дают 76 при разбросе в 18). С трёх медиана становится средним элементом, и один выброс её уже не сдвигает.

Ручной интервал порогом не ограничен и работает с первой же отметки: там срок назвал человек, а не статистика. Это же и есть предусмотренный 01-Проект второй путь — «задан вручную либо посчитан как медиана собственной истории», — и подсказка на экране теперь прямо к нему подталкивает.

Минимум и максимум разброса показываются с первого интервала: это факты из истории, а не оценка, соврать они не могут. Медиана в разбросе стала `number | null`.

Цена: на перенесённых данных срок сохраняет одна позиция из девятнадцати — педикюр с пятью интервалами. Остальные ждут отметок или ручного интервала. Экран станет беднее, зато перестанет выдавать догадку за расчёт.

### Р-28 · Экран «Сейчас»: срочное сверху, остальное по категориям
08.09.2026

Плоский список по срочности отменяется. Сверху блок «Требует внимания» — просроченное и подходящее к сроку, без разбивки. Ниже всё остальное группами по категориям в порядке 01-Проект: Гигиена, Дом, Техника, Авто, Дача, незнакомые категории в конец по алфавиту. Внутри каждой группы — по срочности.

Причина отмены: когда просроченного одна позиция, а девятнадцать «в норме», плоский список перестаёт отвечать на вопрос «что делать» и превращается в перемешанный перечень, где гигиена соседствует с автомобилем без всякой связи.

Причина, по которой срочное всё-таки не разложено по категориям: просроченный таймер на даче ушёл бы в последнюю группу в самый низ экрана. Срочность — единственное, ради чего экран открывают ежедневно, и терять её ради стройности нельзя.

Группировка живёт в расчёте (`groupByCategory`), но порядок категорий передаётся снаружи: сам расчёт не знает, что категории называются по-русски.

### Р-29 · Ручной интервал не подменяется медианой, но расхождение видно
08.09.2026

Уточняет Р-27. Вопрос: когда у позиции с ручным интервалом наберётся достаточно отметок, должна ли медиана его заменить.

Не должна. Ручной интервал и медиана отвечают на разные вопросы: первый — «как надо» (щётку положено менять раз в 90 дней, это норматив, из поведения он не выводится), вторая — «как есть» (по факту раз в 137). Молчаливая подмена стёрла бы ровно то, ради чего дневник и ведётся: приложение начало бы считать привычку нормой и перестало о ней сообщать.

Но и прятать медиану нельзя. Поэтому она считается всегда, как только хватает интервалов, и лежит в `CycleState.byHistory` рядом с действующим `interval`. На экране позиции показывается строка «задано руками N, по факту выходит M — реже задуманного в K раза» и кнопка «Считать по истории» в один тап.

Кнопка обнуляет `intervalDays`, а не подставляет текущую медиану: подстановка заморозила бы снимок сегодняшнего дня, а обнуление переводит позицию на медиану, которая дальше живёт вместе с историей.

Цена: на экране позиции с ручным интервалом появляется лишний блок. Он молчит, пока расхождения нет или пока истории не хватает.

### Р-30 · Куст внутри категории — поле `group`, а не сущность «вещь»
08.09.2026

Категория оказалась слишком крупным делением. «Барьер Эксперт (3 стадии)» и «Барьер Эксперт (2я стадия)» — это один фильтр с двумя расходниками, в Obsidian они жили одной таблицей, а приложение разнесло их по общему списку категории «Дом». То же с зарядками и с батарейками сигналки.

Заведено необязательное поле `CycleItem.group` — свободная строка, как и `cat`. Три уровня: категория → куст → позиция.

Отдельная сущность «вещь» (с датой покупки, ценой, ссылками из позиций) отвергнута. Она выглядит правильнее и открыла бы срок службы вещи напрямую, но противоречит принципу Р-14 «не плодить сущности там, где хватает поля», а 01-Проект прямо говорит, что срок службы вещи механически то же самое, что процедура. Когда куст понадобится сам по себе — со своей ценой и датой покупки, — это будет отдельное решение с настоящим основанием, а не догадка наперёд.

Схему это не двигает: `SCHEMA_VERSION` остаётся 1. Необязательное поле не требует ни нового хранилища, ни индекса, ни переписывания записей — старые записи просто без него, старый код его не заметит. Это тот случай, о котором говорит Р-24: аддитивное изменение, для которого не нужна даже миграция.

Кусты и одиночные позиции стоят в одном ряду и сортируются по самой срочной позиции внутри — иначе просроченный картридж уезжал бы вниз только потому, что его позицию объединили с соседней. Куст из одной позиции остаётся кустом: заголовок не должен исчезать оттого, что вторую позицию удалили.

### Р-31 · Исправленный файл переноса объявляет себя новее сам
08.09.2026

Дополняет механику переноса. Записи из файла помечались неподвижным `SEED_UPDATED_AT`, чтобы файл не затирал правки, сделанные в приложении позже. Побочный эффект вскрылся сразу: исправленный файл — дописали кусты — при повторной загрузке тоже не побеждал, потому что штамп у него тот же. Загрузка проходила «успешно» и не меняла ничего.

Файл теперь может нести необязательное поле `seedUpdatedAt`. Нет поля — прежнее поведение, файл считается зафиксированным в прошлом. Есть — оно и становится `updatedAt` всех записей этого файла, и по общему правилу слияния побеждает файл.

Идентификаторы от штампа не зависят и остаются прежними: иначе исправленный файл не обновил бы записи, а завёл бы вторые такие же.

Цена: подняв штамп, ты соглашаешься, что файл затрёт всё, что успел поправить в приложении по этим записям. Это осознанное действие — правка руками в JSON, — и другого способа сказать «файл теперь главный» нет.

### Р-32 · Отправка одним коммитом, конфликт ловится на ветке
09.09.2026

Уточняет шаги 4–5 раздела «Синхронизация» в 02-Архитектура, где сказано «пишем обратно с указанием версии». Это описание Contents API: там пишется один файл за запрос, с проверкой его sha, и каждый такой запрос — отдельный коммит. Абзацем ниже тот же документ требует «одна синхронизация — один коммит», и одновременно выполнить оба условия нельзя.

Выбран Git Data API: дерево собирается целиком, коммит один, ветка двигается одним запросом без `force`. Проверка версии переезжает с отдельного файла на ссылку ветки — если второе устройство отправило раньше, отказ приходит на весь пуш, а не на один файл. Это строже прежнего и ровно то, что нужно: смысл проверки в том, чтобы чужая отправка не потерялась.

Поведение при конфликте не меняется: перечитать, слить заново, максимум две попытки, потом отложить. `force` не используется нигде — приложение не должно уметь затирать чужую работу даже по ошибке.

Цена: пять запросов на отправку вместо одного на файл и больше кода в клиенте. Взамен история репозитория читается по одной строке на синхронизацию, а не по строке на файл.

**Дополнение от 09.09.2026, по факту первого запуска.** Git Data API не работает на репозитории, в котором нет ни одного коммита: 409 «Git Repository is empty» отвечают и чтение ветки, и создание дерева. Ему нужен существующий коммит, от которого отсчитываться. Обходной путь взят из документации GitHub: первый файл (`meta.json`) кладётся через Contents API, он же создаёт коммит и ветку, дальше всё идёт общим путём.

Цена — два коммита один раз за жизнь репозитория. Правило «одна синхронизация — один коммит» это не отменяет: заведение репозитория происходит однажды и синхронизацией не является.

Записано отдельно потому, что ошибка была предсказуемой и я её не предсказал: 409 разбирался как гонка, повторялся дважды и выходил наружу английским текстом от GitHub. Проверка была написана на догадку о поведении GitHub, а не на его настоящий ответ.

### Р-33 · Дерево пересобирается целиком, `dirty` не выбирает файлы
09.09.2026

Дополняет Р-18, оставляя его в силе: раскладку по-прежнему делает `sync`, а не `db`. Меняется то, откуда `sync` берёт список файлов на отправку.

Было задумано: собрать файлы по пометкам `{store, id}` из очереди изменений. Не работает в одном обычном случае — у отметки поправили дату, и год сменился. Запись должна исчезнуть из `cycles/2025.json` и появиться в `cycles/2026.json`, а по пометке «запись такая-то изменилась» прежнее её место не восстановить. Осталась бы вторая копия, живущая на сервере вечно.

Теперь дерево файлов собирается из базы целиком, для каждого файла считается тот же отпечаток, которым содержимое называет git, и отправляются только те файлы, чей отпечаток разошёлся с деревом на сервере. Скачивать для сравнения ничего не надо. Побочно чинится файл, испорченный на сервере, и восстанавливается удалённый.

Требование, без которого это не работает: одинаковые данные обязаны давать побайтово одинаковый файл. Порядок ключей в объекте зависит от того, как запись собиралась — из формы, из переноса или с сервера, — поэтому ключи сортируются, а записи выстраиваются по `id`. Отпечаток считается по байтам, а не по символам: в заметках кириллица, и на ней эти числа расходятся вдвое.

«Прошлые годы после закрытия не переписываются» (Р-08) держится: их содержимое не изменилось, отпечаток совпал, в коммит они не попадают. Опустевший год перезаписывается пустым списком — но только если его файл читали на этом же проходе, иначе можно затереть непрочитанное.

Очередь `dirty` остаётся: она отвечает на вопрос «есть ли что отправлять» и показывает счётчик на экране. Выбирать файлы она больше не пытается.

Цена: сериализация всей базы на каждый проход. На сотнях записей это доли миллисекунды; когда их станут десятки тысяч, придётся вернуться.

### Р-34 · Запись без даты — в `<модуль>/undated.json`

Год по времени создания записи отвергнут дважды. Поля `createdAt` в модели нет вовсе. Вывести время из `id` тоже нельзя: ULID его несёт, но у перенесённых из Obsidian записей идентификаторы детерминированные, выведенные из естественного ключа (Р-31), и никакого времени в них нет.

Побочная польза: запись с испорченной датой не теряется молча, а оказывается в отдельном файле, где её видно и можно поправить руками. Терять запись из-за одной кривой строки нельзя ни при каких обстоятельствах.

### Р-35 · Заправки и деньги — не сюда
09.09.2026

Вопрос: заводить ли модуль автомобильных трат — ремонт, заправки, страховка.

Разделено надвое. Ремонт и обслуживание уже описываются циклами: у них есть интервал, есть «просрочено», а цена собирается в `CycleEvent.price`. Отдельный модуль им не нужен — нужен экран стоимости владения, который давно висит в открытых вопросах.

Заправка в эту механику не ложится вовсе: у неё нет интервала, и «просроченная заправка» — бессмыслица. Осмысленный вывод из неё — рубли на километр и расход топлива, то есть сумма за период, а не срок до следующего раза. Это финансовый учёт, и место ему в приложении про траты, рядом со страховкой, штрафами и кешбеками, которые пока живут в Obsidian. Граница та же, что с едой и досугом: здесь событие с датой, там деньги.

Связь между приложениями, когда финансовое появится, обеспечивает `refs` — оно зарезервировано в модели с первого дня.

Открытым остаётся пробег: масло меняют не «раз в 300 дней», а «раз в 10 000 км», и для авто интервал по дням врёт. Это не модуль трат, а второй вид интервала у позиции цикла. Записано в открытые вопросы, решается не раньше, чем циклы отработают год на реальных данных.

### Р-38 · Сумма показывается только вместе с числом отметок
09.09.2026

Уточняет Р-36 в двух местах: в требовании к самой сумме и в порядке работ.

**Требование.** Сумма никогда не показывается в одиночку. Рядом всегда стоит,
из скольких отметок она сложена, и сколько отметок всего: «6 118 ₽ за
4 отметки из 33». Первое число отвечает на вопрос «дорого ли это» — три тысячи
за шесть стрижек и три тысячи за одну это разные новости, а голая сумма их не
различает. Второе отвечает, насколько сумме можно верить: цена стоит у четырёх
отметок, остальные двадцать девять в неё не вошли.

**Порядок.** Р-36 требовал сделать расчёт сумм после того, как поле цены
поработает и данные накопятся. С числом отметок рядом ждать больше незачем.
Возражение Р-36 было против стоимости владения в месяц: она делит деньги
на интервал, которого у большинства позиций нет, и выдаёт догадку за расчёт.
Сумма ничего не делит, а с обоими числами она остаётся правдой и на четырёх
ценах из тридцати трёх — да ещё и показывает, сколько не заполнено. Поле ввода
и суммы делаются одним заходом.

**Где вводится цена.** Двумя путями, и второй обязателен. Поле рядом с датой
в форме отметки задним числом — это то, что было записано в плане. Но отметка
на экране «Сейчас» ставится одним тапом, формы там нет вовсе, и почти все
отметки приходят оттуда: через одну только форму цена не попала бы в базу
никогда. Поэтому цена правится прямо в строке истории на экране позиции.

**Где показывается.** По позиции — под историей отметок. По кусту и категории —
свёрнутый блок «Траты» на экране «Сейчас». Куст остаётся главным уровнем
сложения, как и записано в Р-36.

Стоимости владения в месяц по-прежнему нет, и Р-36 в этой части в силе.

### Р-40 · График — свой на SVG, без библиотеки
09.09.2026

Закрывает открытый вопрос «Библиотека графиков», заведённый с пометкой
«решается на этапе 3».

Графиков в приложении ровно один вид: числовой ряд по календарю — вес, потом
давление. Точек за год набегает сотня-другая. Любая библиотека под это тянет
от пятидесяти килобайт, и это килобайты в приложении, которое обязано
открываться без сети мгновенно и обновляться через service worker целиком.

Своё решение — это ломаная по точкам и две подписи. Арифметика вынесена
в `modules/health/chart.ts` и покрыта тестами: раскладка точек по осям — то,
что может соврать незаметно, и проверять её глазами бесполезно. С библиотекой
эта часть была бы чужой и непроверяемой, а рисование всё равно пришлось бы
настраивать руками.

Отдельно записано главное требование, которое библиотека по умолчанию не
выполняет: **ось X — календарное время, а не порядковый номер точки.**
Три взвешивания в январе и одно в июне — это три точки слева и одна справа.
По номерам они встали бы через равные промежутки, и кривая соврала бы про
скорость изменения — то есть ровно про то, ради чего график и рисуют.

Пересмотреть стоит, если понадобятся столбики, несколько рядов на одной оси
и зум. Пока не понадобились.

### Р-41 · Вместо тестов React-экранов — прогон в браузере
10.09.2026

Записывает решение, которое до сих пор жило только в Журнале, и уточняет его.

**Тестов React-экранов не заводим.** Причина прежняя: приложение
однопользовательское и открывается каждый день, сломанный экран виден в тот же
день, а тесты экранов — самый хрупкий их вид: они ломаются от перестановки
разметки, не поймав ни одной настоящей ошибки. Вместо них дисциплина «логика
вне компонента»: расчёт живёт в `modules/<имя>/<имя>.ts` и покрывается тестами
целиком, а компонент только рисует.

**Но дисциплины оказалось мало.** За два этапа пять ошибок вылезли именно
в React — там, где тестов нет. Три поломки Этапа 2 нашлись на первом живом
запуске с телефона, две ошибки Этапа 3 — исключение на нечитаемой дате в списке
и строка «не болел столько-то», спрятанная фильтром по году, — нашлись бы там же.
«Виден в тот же день» верно, но день этот тратится на выяснение вместо минуты
до пуша.

**Заводится `scripts/smoke.mjs`.** Он собирает приложение, открывает его
в headless-браузере и проходит обычный путь человека через оба модуля: завести
позицию, отметить, вписать цену, посмотреть траты, завести эпизод с симптомом,
закрыть его, открыть сводку. Пятнадцать проверок и ни одной ошибки в консоли —
условие прохода.

Чем он **не** является: это не тест экрана и не проверка вёрстки. Он отвечает
на один вопрос — открывается ли приложение и не падает ли оно на обычном пути.
Расчёт по-прежнему проверяется обычными тестами, и переносить проверки туда
нельзя: прогон медленный, хрупкий по таймингам и молчит о причине.

**Playwright не берётся.** Ради одного сценария он тянет свой Chromium и сотню
мегабайт в `devDependencies`. Скрипт работает через протокол отладки поверх
WebSocket, встроенного в Node 22+, на уже установленном браузере. Ни одной новой
зависимости — то же правило, по которому иконки рисует свой скрипт (Р-20).

**Собирает он сам, а не полагается на `dist` от прошлого раза.** Это выяснилось
сразу: первая версия запускалась на вчерашней сборке и показывала зелёное на
намеренно сломанном коде. Прогон, который молча проверяет не тот код, хуже
отсутствующего.

Цена: полторы минуты на прогон и сценарий, который придётся дописывать с каждым
модулем. Взамен — ошибки вида «белый экран» находятся до пуша, а не на телефоне
через неделю.

### Р-42 · Закончено считается по статусу, а не по дате окончания
10.09.2026

Уточняет пункт Плана Этапа 4 «начато против закончено» и снимает противоречие
между ним и данными.

**Как есть.** У всех 72 записей контента, перенесённых из Obsidian, поле `end`
пусто. Не у части — у всех до единой: в дневнике просмотренного даты окончания
не было как графы. Взяться ей теперь неоткуда, вспомнить её через год нельзя.

По букве Плана «закончено» — это записи с датой окончания, и экран итогов
показал бы «начато 72, закончено 0». Число формально верное и полностью ложное
по смыслу: 67 из этих записей досмотрены, и автор это знает.

**Как решено.** «Закончено» — это статусы `done` и `dropped` вместе. Правду про
исход несёт статус, `end` несёт только дату, а даты может не быть. Брошенное
считается законченным: решение больше не смотреть — это результат, а не пауза,
и по 01-Проект статус «бросил» заведён именно ради того, чтобы такие записи
не висели незакрытыми вечно. В строке итогов брошенное при этом называется
отдельным числом — «начал сорок и бросил двадцать» и «начал сорок и досмотрел
сорок» обязаны читаться по-разному.

**Что с полем `end`.** Остаётся в модели необязательной датой той же точности,
что и `start` (Р-25). В форме спрашивается только у законченного и подписано
«если помнишь». Удалять его из модели незачем: у записей, заведённых в
приложении, дата окончания известна, и терять её было бы жаль. Считать по ней
что-либо — нельзя, пока она не проставлена у большинства.

Это тот же принцип, по которому сумма трат идёт с числом отметок (Р-38):
показывать надо то, что известно, и ровно с той уверенностью, с какой известно.

### Р-43 · Настройки — не вкладка, а шестерёнка
10.09.2026

Закрывает вопрос «пятая вкладка», висевший в Журнале с 10.09.2026 в блоке
«Не описано в документах».

**Повод.** Этап 4 добавляет вкладку «Контент», и вкладок становится пять.
Выяснилось, впрочем, что панель не помещается уже при четырёх: на телефоне
подписи уезжают вбок, и до «Настроек» приходится мотать. Причина в вёрстке —
`min-width: auto` у элементов флекса не даёт подписям сжиматься, — но починка
вёрстки только отодвинула бы порог.

**Решено.** «Настройки» уходят из нижней панели в шапку экрана «Сейчас»
шестерёнкой. Панель остаётся из четырёх ежедневных вкладок: Сейчас, Здоровье,
Контент, Лента.

Причина не в тесноте, а в частоте. В настройки заходят раз в месяц — вписать
токен, проверить срок, сделать выгрузку, — а место в панели они занимали
наравне с тем, что открывают ежедневно. Приложение открывается на «Сейчас»,
так что шестерёнка — тот же один тап от старта, каким была вкладка.

**Точка синхронизации переезжает туда же.** Она и выигрывает от переезда:
раньше висела на дальней вкладке, до которой надо было домотать, теперь стоит
на первом экране при запуске.

**Отвергнутые варианты.** Убрать «Ленту» до Этапа 5 — она заглушка, но убирать
и возвращать вкладку глупо: человек привыкает к месту. Сделать панель явно
прокручиваемой — честно по отношению к тому, что уже происходит, но до
настроек по-прежнему надо мотать. Иконки вместо подписей — вводит целый
визуальный язык ради одной строки текста.

Цена: настройки открываются только с «Сейчас». Для экрана, куда заходят раз
в месяц, это приемлемо; если окажется неудобным, шестерёнка добавится в шапки
остальных экранов — это правка одной строки в каждом.

### Р-44 · Месяцы заголовками, статусы переключателем
10.09.2026

Три просьбы с экрана после первого дня работы с контентом, решённые одним
заходом: фильтр по месяцам, аналитика по месяцам в итогах, отдельные списки
для брошенного и запланированного.

**Месяцы — заголовками над пачками записей, а не фильтром.** Просьба звучала
как «фильтры по месяцам, как у меня было в Obsidian», и вторая половина
уточняет первую: в Obsidian дневник вёлся разделами по месяцам — заголовок
месяца, под ним всё, что за месяц набралось. Это не фильтр, а разбивка.

Разбивка и лучше по существу. Фильтр показывает один месяц ценой тапа и прячет
остальные одиннадцать; заголовки показывают год лентой целиком, и «что я смотрел
весной» читается прокруткой, а не перебором. Выбор года над списком остаётся —
он режет объём, а не прячет.

Отбор по месяцу при этом умеет `filterEntries` — он написан и покрыт тестами.
Экран его пока не вызывает: понадобится, когда лет станет много, и тогда это
будет ряд чипов, а не новая механика.

**Статусы — переключателем над одним списком.** Просмотренное, брошенное
и «к просмотру» отвечают на однотипный вопрос — что это было и когда, — и
различаются одним полем. Три блока подряд разъехались бы по экрану, а список
«к просмотру» до этого стоял внизу, ниже итогов, куда не долистывают.

«Смотрю сейчас» в переключатель не входит и остаётся блоком наверху. Это
не раздел архива, а ежедневное действие: досмотрел и поставил оценку. Второе
место для него развело бы одну запись по двум спискам — та же причина,
по которой открытые эпизоды в здоровье стоят отдельно от истории.

**Аналитика по месяцам в итогах** — столбики «сколько начато в каждом месяце»,
как сезонность болезней, плюс строка про самый плотный месяц. Строка молчит
при ничьей и когда в месяце всего одна запись: «плотнее всего январь — одна
запись» не наблюдение, а пересказ данных. То же правило, по которому молчат
среднее без числа записей (Р-38) и срок по одному интервалу (Р-27).

### Р-45 · Фильтр по месяцам — вдобавок к заголовкам, а не вместо
10.09.2026

Уточняет Р-44 в одном месте. Там сказано, что отбор по месяцу написан
и покрыт тестами, но «экран его пока не вызывает: понадобится, когда лет
станет много». Это оказалось неверно уже на второй день: просьба повторилась
прямо, отдельно от разбивки — «он по месяцам отражает одним листом, а хотелось
бы ещё фильтр по месяцам, там же, где фильтр по типу».

Прежнее рассуждение подменяло один вопрос другим. Заголовки отвечают на «что
было за год» — год листается лентой, и месяцы служат вехами. Фильтр отвечает
на «покажи апрель» — когда месяц известен заранее и остальное мешает. Второй
вопрос от первого не производен, и разбивка его не закрывает.

**Обе вещи остаются.** Ряд чипов встаёт под фильтром по типу, разбивка
заголовками не трогается: при выбранном месяце группа просто остаётся одна.

Два правила, оба ради того, чтобы список не пустел молча:

- **В ряду только непустые месяцы.** Чип на месяц без записей — это тап,
  ведущий к «ничего не нашлось». То же правило, по которому отбираются годы.
- **Месяц сбрасывается при смене года и статуса.** Апрель, выбранный
  в просмотренном за 2026-й, у брошенного может не существовать вовсе.

Месяцы при этом считаются по статусу и году, но **не** по типу: иначе ряд
перестраивался бы под пальцем при каждом переключении соседнего фильтра.

### Р-46 · Период по умолчанию — свежий год, записи без даты — отдельный выбор
10.09.2026

Вопрос с экрана: «когда появится 2027-й, что будет с „Весь год“?»

Ломалось три вещи, и только первая была видна в вопросе.

**Подпись.** «Весь год» при выборе «всё время» означала бы «все годы».
Названа «Все месяцы» — правда при любом выборе периода.

**Умолчание.** Список открывался на «всё время». Пока год один, это то же
самое; со второго года экран стал бы вываливать оба разом, и чем дальше, тем
длиннее. По умолчанию теперь свежий год — так же, как в «Итогах» и в итогах
здоровья. Ряд годов по-прежнему не показывается, пока год один: переключать
нечего.

**Записи без даты.** Отбор по году отбрасывает запись, дата которой не
читается, — а Р-34 заводит для таких записей отдельный файл ровно затем, чтобы
их было видно и можно было поправить руками. С умолчанием «всё время» они
попадались на глаза сами; с умолчанием «свежий год» стали бы невидимы.

Заведён отдельный выбор «без даты» рядом с годами. Появляется, только если
такие записи есть: в норме их нет, и пустой чип занимал бы место зря. У списка
«к просмотру» не показывается вовсе — там даты нет у всех по определению
(Р-21), и отдельный чип для этого случая бессмыслен.

Общее у трёх правок одно: **фильтр не должен прятать записи молча.** Тот же
принцип уже стоит за сбросом месяца при смене года и статуса (Р-45) и за тем,
что в ряду только непустые месяцы.

## Открытые вопросы

- **Дневник Депры.** Ежедневная шкала, а не эпизоды с началом и концом. Тип данных четвёртый. Решение о включении в приложение не принято.
- **«Ту Бумги» и «Исходров».** Содержание не выяснено, классификация не проведена.
- **Включающее обслуживание.** Замена всех трёх стадий фильтра «Барьер Эксперт» заодно меняет и вторую стадию, у которой свой срок втрое короче. То же будет с ТО автомобиля, включающим замену масла. Сейчас лечится руками: при полной замене ставятся две отметки. Кодом это поле вида «засчитывать отметки такой-то позиции», то есть связь между позициями внутри модуля — заводить её по одному случаю преждевременно. Пересмотреть, когда наберётся третий: два повода уже видны.
- **Интервал по пробегу, а не по дням.** Замена масла привязана к километрам, а не к сроку, и для авто расчёт по дням врёт. Механически это второй вид интервала у позиции цикла плюс где-то записанный одометр. Заводить по одной категории преждевременно — вернуться, когда циклы отработают год (Р-35).
